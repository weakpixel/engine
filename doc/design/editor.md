# Level editor

How the level editor is built and why. The API is in the guide: [engine/editor.md](../guide/engine/editor.md).

## Shape

```
VSCode extension (weakpixel-engine-vscode)    webview (Chromium)
  level file = TextDocument  ── postMessage ──>  host script ── weakpixelHost.toGame ──> bridge.Bridge
  undo, save, diff, outline  <── postMessage ──  (media/)     <── weakpixelHost.fromGame ── (game.Tool)
                                                                                        └ editor.Session
                                                                                          └ game.Engine (wasm)
```

- **The game is the viewport.** The user's own game, built for js/wasm with `-tags editor`, runs in the editor tab through [`editor/host`](#the-host-and-the-stages). Only that binary knows the game's components, systems and Lua bindings, so the extension builds it rather than shipping a generic player. An incremental wasm build takes about two seconds.
- **One core, any shell.** `editor.Session` is a `game.Tool` with no UI: selection, picking, dragging, the editor camera, applying documents and Play/Stop. `bridge.Bridge` puts a JSON protocol in front of it. An in-engine shell (Go widgets) or a native process speaking the same protocol over stdin/stdout could drive the same core.
- **The document owns undo.** The level file is a VSCode `TextDocument`. The viewport never changes the level on its own authority: a drag ends with an `edit` message, the extension turns it into a minimal `WorkspaceEdit`, and the changed text comes back to the game as a `document`, which `Session.Apply` applies by id. Typing in the JSON, undo, redo and git checkout all take that same path. The session counts the JSON of its own edits as already applied, so the echo changes nothing.
- **The MCP server is a second document backend.** `wpix mcp` ([tools.md](../guide/tools.md#mcp)) edits the same files without VSCode: its edit tools compute minimal splices with `jsonedit`, check the result offline against the merged GOD, and write the file. The file stays the single source of truth, so a game or an editor that has it open takes the change as any other edit of the text.
- **Ids are identity.** Every object in an editor document has an `"id"`. Entities change across Play/Stop and class changes; ids do not. The extension can rename an id and then rewrites the fields of the level that refer to it, as a best effort (see its [README](https://github.com/weakpixel/weakpixel-engine-vscode#readme)); the engine only sees the changed document.

## The host and the stages

**The engine owns the entry.** Running the game's own `main` in the editor was brittle: it ran whatever `main` did (flags, window calls, `log.Fatal` on a missing file), every game copied the same bridge, `httpfs` and FS layering code, and the game hard-coded which level the editor owned. `editor/host` is the entry of an editor build instead. The game describes itself (`host.Game`: config, systems, prefab rendering) and the host connects the bridge, builds the FS, creates the engine and opens the file. A second `main` behind the `editor` build tag keeps the game's own `main` out of the wasm; both share the game's config and setup functions, so no package split is needed. Rejected: generating a main with `go build -overlay` (hides what runs), and a generic player shipped by the engine (it would not know the game's components, systems or Lua bindings).

**Two stages, one wasm.** A level is edited among the game: its systems run in edit mode if they opt in ([`game.EditRunner`](../guide/engine/engine.md#development-tools)) and its map is its backdrop. A prefab used to open the same way, so it sat at (0, 0) in the middle of a world, with the hero, the camera rig's bounds and a Play that ran the whole game around it. The prefab stage starts none of the game's systems and no levels, resets the camera rig, paints a neutral background and draws a grid and the origin over the picture (`editor.Stage`, drawn in `DrawFinal` in window pixels). Play and Step are no-ops. Rendering the prefab like the game does (layers, post effects) is the game's `Game.Prefab` hook.

**The page names the stage.** The extension sets `weakpixelHost.stage` (`level` or `prefab`, by file suffix) and `weakpixelHost.path` (the first file's asset key) beside `assetBase`. Ebiten runs one game per process, so a change of stage reloads the page; switching between two files of the same stage uses `open`. These page fields are not protocol messages (`bridge.Version` is unchanged).

**Listing.** HTTP cannot list directories, so the page also sets `weakpixelHost.files`: the asset keys of every file under the asset root, read when the page is made. The host lists directories from that index (plus `Game.FS`'s files) and reads the files themselves over HTTP, so the editor build needs no embedded copy of the assets and the library scans the real folder. A file created while the editor runs is read at once but joins the library's listing on the next page load. Not built: re-scanning the library on `assetsChanged`. Page fields, not protocol messages (`bridge.Version` is unchanged).

**Backdrop.** `Session.OpenAt` calls `Config.OnOpen` before it opens the document; the host uses it to unload the previous backdrop and load the next one's when the target changes: per file, the sibling `<name>.tmj` (`NoDocuments`), else the sibling `<name>.world` or the package's own level `<pkg>/<pkg>` (`LoadLevelBase`, `SkipDocuments` with the edited file), since the session spawns the edited document itself. A custom `Game.Backdrop` is still called per package.

**The native transport.** A native host reaches the game the same way, over loopback TCP instead of the page's script (`bridge.DialHost`). The host listens on `127.0.0.1:0` and starts the editor build with `WEAKPIXEL_BRIDGE` (the address), `WEAKPIXEL_BRIDGE_TOKEN`, `WEAKPIXEL_STAGE`, `WEAKPIXEL_PATH` and optionally `WEAKPIXEL_HEADLESS=1` ([variables](../guide/engine/engine.md#host-variables)); `host.PageFromHost` and `bridge.ConnectHost` read them where the browser build reads `globalThis.weakpixelHost`. The game sends the token as the first line, then each message is one JSON object per line (a JSON text holds no raw newline). Stdin and stdout were rejected because games print to stdout, and extra file descriptors because `exec.Cmd.ExtraFiles` does not exist on Windows. When the host closes the connection the bridge quits the engine at its next tick. A headless run (`host.RunHeadless`) calls `Engine.Update` on a ticker without `ebiten.RunGame`, with no sound and a manual input source; since nothing is drawn, a `screenshot` is never answered, which the host must know. This is a transport only: no message or field changed, and `bridge.Version` is unchanged. The first user is `wpix mcp` ([tools.md](../guide/tools.md#the-game)), whose host side is `tools/internal/mcpserver`. It cannot import `bridge` (Ebiten), so it repeats the message shapes and a test checks the constants.

**A round trip is a `status`.** The bridge handles queued messages at the start of a tick and answers them in order, so the `status` answer to a `status` sent after a request says that the game handled the request and that every answer to it arrived. The MCP server sends one after each request (and twice, to know that a `step` ran).

## Applying a document

`Session.Apply` decides per object whether its entity is kept (same id, class, prefab and part), created (new id, class or prefab) or deleted (id gone), and per component whether to set it (compact JSON changed), remove it (optional or extra component gone) or leave it alone. Leaving unchanged components alone keeps runtime state (animation frames, values a paused game system wrote) and avoids archetype moves. Entities for new objects are created before any component is decoded, so references to them resolve; if any component fails, those entities are deleted and the World is as before. When objects were created or deleted, components with entity references are decoded again even if their text is unchanged, because the entity behind an id may be new.

**Prefab instances are expanded first.** `types.Prefab.ExpandInstance` turns an instance entry into plain objects: its overrides (`components`, and `children` for the other objects of a [multi-object prefab](../guide/ecs/game-object-definition.md#multi-object-prefabs)) merged over the prefab's objects, the parts with ids `<id>/<part>`. Everything after compares merged components, so a saved prefab is just another document version: the session keeps a stamp (`Version`, state) of every prefab it used and re-applies the current document when one changes. Prefabs load asynchronously and `Apply` must stay synchronous for a shell that answers every document, so a document with a loading prefab is kept as pending and finished in an edit tick; the bridge answers its `document` then. Drags of instances are reduced to overrides in Go (`types.Prefab.PartOverrides`, against the prefab's object expanded for that instance), where the schema is known, so the extension never diffs; it only merges, to show values. Without `WatchInterval` the asset server keeps no Decode results, so a dependent of a changed asset (a variant of a saved base) is read from its file again instead of re-finished.

## Modes

Edit mode is `game.TickPause` every tick: the engine's own stages run (assets, snapshot, animation, extract, audio), game systems and the input stage do not. The editor polls the device source itself because the paused input stage does not; pad connects it consumes are handed to the game's next poll. Play is `TickRun`, and `TickPause` while a `pause` holds it (no reset; `step` returns `TickStep` once, as in edit mode). Stop deletes the entities that did not exist when Play started (everything the game spawned), re-applies the document with every component forced and clears every tween, so no tween started during Play keeps animating the restored objects. Game state outside the level is the game's business (`Config.OnReset`).

**Pacing.** Ebitengine in a browser runs one frame per `requestAnimationFrame` and calls `Draw` every frame whatever the TPS, and `Engine.Draw` renders the whole queue each time, so a lower TPS alone saves little. The session therefore picks the tick rate (idle, active, the game's own in Play, hidden) and is a `game.DrawGate` that draws only the first frame after a tick in edit mode, and only when that tick changed the picture (`Engine.FrameChanged` compares the extracted queue with the last drawn one, which is cheaper than drawing it); `editor/host.Run` sets `SetScreenClearedEveryFrame(false)` so a skipped frame keeps its image, and Ebitengine stops presenting after a few unchanged frames. `FPSModeVsyncOffMinimum` with `ScheduleFrame` is not used: it is deprecated and forces TPS to follow the frame rate. The rate changes from other goroutines go through `ebiten.SetTPS`, which is safe there; the pacer compares with the actual rate each tick instead of its own last value. Pacing is on in every editor build; the rates and the states are in the [guide](../guide/engine/editor.md#pacing). The cost that remains follows the drawn frames, not the ticks: Ebitengine presents for a few frames after each modified one, and under software rendering each present is most of the work. Measured in the studio under Xvfb (llvmpipe), the test game's animated level in edit mode went from about 250% of one core to about 130%; the same level at 1 idle tick a second used under 30%.

**Switching files.** One game shows one file at a time. `Session.OpenAt(path, text)` replaces the level with another file's document: it stops Play as Stop does, clears the selection, takes `path` as the level's path and asset scope, and frames the new level unless the shell restores a camera with `SetCamera` afterwards (a camera restored before `Open` survives it; one restored before `OpenAt` does not). A document that does not parse changes nothing. The bridge's `open` message calls it, so a shell switches files without reloading the game.

## Protocol

JSON objects with a `"type"`, version 0 (`bridge.Version`, sent in `ready`; it stays 0, with no compatibility code, until the first release). Components are named by their key `group:name` ([identity](../guide/ecs/game-object-definition.md#identity)) everywhere: in documents, `edit.component`, the first element of a `field` path and error texts. The bridge queues incoming messages and handles them at the start of the next tick, on the game goroutine, because a JavaScript callback can run while the game goroutine is blocked mid-frame.

| Direction | Type | Fields | Meaning |
| --- | --- | --- | --- |
| game → host | `ready` | `version`, `schemas`, `components`, `assetKinds` | First tick. `schemas` is every registered object schema (`{group, class, doc?, goType?, components}`, the GOD's object entry); each component is `{component: "group:name", field, optional?, readonly?, schema, doc?, embeddedVia?}` (the GOD's object component entry with its `schema`). `components` is every registered component type, `{group, name, doc?, goType?, schema}` sorted by key: an object may hold any of them ([extra components](../guide/ecs/game-object-definition.md#extra-components)), so the inspector offers them. `assetKinds` maps file suffixes to asset kinds. |
| game → host | `applied` | `error` | Answer to each `document` and `open`; `error` is `""` when it was applied. A document waiting for prefabs is answered once they loaded; a saved prefab that re-applied the document sends one unasked. |
| game → host | `objects` | `objects: [{id, group, class, prefab?, part?}]` | The level's objects after an open or apply; `prefab` is an instance's prefab key, `part` the id within the prefab of an object of a multi-object instance that is not its root (its `id` is `<root id>/<part>`; parts follow their root). |
| game → host | `selection` | `ids` | The selection changed in the viewport (or objects disappeared). |
| game → host | `edit` | `id`, `component`, `json`, `override?`, `part?` | A drag ended: replace the value of that component (its key, `gfx:Transform`). With `override` (a prefab instance) `json` is the component's override; `{}` drops it. With `part`, `id` is the instance root and `json` the override of that part, for `children.<part>` of the entry. |
| game → host | `mode` | `play`, `paused?` | Play or Stop happened, or a `pause` paused or resumed Play (`paused` is set while Play is paused). |
| game → host | `entities` | `entities: [{entity, id?, components, errors?}]`, `truncated`, `missing?` | Answer to `inspect`: the live values. `entity` is `"<index>.<generation>"`, `id` the document id (none for an entity a system spawned), `components` every component the types registry knows that the entity has, encoded as the document holds them (asset keys, ids; a reference to an entity that is no level object is written `"#<index>.<generation>"`), `errors` those that failed to encode. Components registered only with `ecs` are not listed: the ecs API cannot name them. `truncated` says the limit cut the list; `missing` lists asked ids with no live object. |
| game → host | `status` | `tick`, `play`, `paused`, `scenes`, `tps`, `draws` | Answer to `status`: the bridge's tick count (the tick that handled the request included), the mode, the names of the engine's scene stack, bottom first, the tick rate of the current [pacing](../guide/engine/editor.md#pacing) state (not the active rate a wake runs the answering tick at) and the frames drawn so far. |
| game → host | `create` | `object` | Append this object (fresh id) to the document. |
| game → host | `choose` | `path`, `x`, `y`, `options` | A drop fits several object types; ask the user, then resend the `drop` with `class`. |
| game → host | `camera` | `x`, `y`, `zoom` | The editor camera stopped moving (about 250 ms after a pan, zoom or frame). |
| game → host | `mapLayers` | `layers: [{map, name, path, kind, layer, hidden}]` | The tile and image layers of the Tiled map behind the level, in draw order (`map` the `.tmj` key, `path` the Tiled layer path, `kind` `tiles` or `image`, `layer` the render layer the game spawned it on, `hidden`). Built from the world's `tilemap.TileLayer` entities and sent when the list changes, not every tick: after an open, once the backdrop is ready, after a map hot reload or a `mapLayerHidden`. An older host ignores it. Object and group layers spawn nothing and are not listed. |
| game → host | `screenshot` | `id`, `png` (base64), `width`, `height`, `tick`, `error?` | A capture: the answer to a host `screenshot` (its `id` echoed), or a capture the game took itself (hotkey, environment variables) with `id` `""`. Under the bridge the game never writes a file: the bridge installs the screenshot sink and the host decides where the PNG goes. On failure `png` is empty and `error` says why (bad target, scale outside 1..8, image over the size limit). Same shape as the tool protocol's, built by `editor/shotproto`. |
| game → host | `error` | `message` | A message could not be handled, or an asset failed to load or reload (a `.kage` that no longer compiles): the host wraps `Config.OnAssetError` with `Bridge.ReportError`. The game's own `OnAssetError` still runs. |
| host → game | `document` | `text` | The level document's current text. |
| host → game | `open` | `path`, `text` | Switch to another file: `text` is its document, `path` its asset key (the level's asset scope and `game.Level.Path`). Play stops, the selection is cleared and the level is framed unless a `camera` follows. Answered like `document`; later `document`s apply to this file. |
| host → game | `assetsChanged` | `paths` | Files under the asset root changed (relative paths): `asset.Server.Changed`. |
| host → game | `select` | `ids`, `reveal?` | Select these objects (from the outline). With `reveal` the camera pans to them when they are not in view (`Session.Reveal`): the union of their bounds must lie inside the visible world rectangle shrunk by 10% per side, else the camera centers on it; zoom is unchanged. Without it the camera never moves. The pan is reported as `camera`. |
| host → game | `mapLayerHidden` | `map`, `path`, `hidden` | Hide or show a map layer in edit mode (`Session.SetMapLayerHidden`): sets `TileLayer.Hidden` of that layer's entity and writes nothing to the map (Tiled owns the file). Play and Stop keep it; a new backdrop or a map hot reload starts from Tiled's visibility again. `mapLayers` reports the result; an unknown layer answers `error`. |
| host → game | `screenshot` | `id`, `target?`, `scale?`, `keepAlpha?` | Take a capture of the next drawn frame (`Engine.Screenshot`): `target` `"game"` (default, the logical frame, post passes included) or `"window"` (final pass and letterbox), `scale` 1..8 for `game`. Answered by `screenshot`; an unknown `target` is answered at once with `error` set. Neither target contains the editor's selection, markers or outlines. |
| host → game | `drop` | `path`, `x`, `y`, `class?` | A file was dropped on the canvas at device pixels `x, y`. A `*.prefab.json` makes an instance of it. |
| host → game | `play`, `stop`, `step`, `frame` | none | Mode commands; `frame` centers the camera. `step` runs one tick in edit mode or in a paused Play. |
| host → game | `pause` | `paused` | Pause (`true`) or resume Play (`Session.Pause`): a paused Play is `TickPause` without a reset, so the game keeps drawing and `step` advances it. Answered with `mode` when it changed; ignored in edit mode. |
| host → game | `inspect` | `ids?`, `components?`, `all?`, `limit?` | Read live values: the level's objects (`ids`, else all in document order), and with `all` every other entity in index order, at most `limit` (default 100), only the component keys in `components` when given. Answered by `entities`. Works in both modes. |
| host → game | `status` | none | Answered by `status`. |
| host → game | `input` | `keys?`, `mouse?`, `pad?`, `ticks?` | Hold input in Play for `ticks` game ticks (default 1) on top of the devices (`Session.Inject`): `keys` by `input.Key` name, `mouse` `{x, y, buttons, wheelX, wheelY}` (logical pixels; buttons `left`, `middle`, `right`, `back`, `forward`), `pad` `{buttons, axes, triggers}` (buttons by their bindings name after `pad:`, axes left x, left y, right x, right y). The pad is a virtual gamepad (`editor.InjectedPad`) announced as connected the first time. A new `input` replaces what is left of the last; edit mode ignores it, Stop drops it, and a paused Play holds it until ticks run. Unknown names answer one `error` and nothing is held. |
| host → game | `camera` | `x`, `y`, `zoom` | Restore the editor camera (after a rebuild, before the document); the level is then not framed on open. Not reported back. |
| host → game | `settings` | `snap?`, `colliders?`, `background?`, `stage?`, `rate?` | `rate` is `{idle?, active?, hidden?}`, the [pacing](../guide/engine/editor.md#pacing) rates in ticks per second (defaults 10, 60, 0; `.weakpixel.json` `editor.rate`); bad rates answer `error` and change nothing. The drag snap grid in world units, 0 for off, `colliders` shows (default) or hides the collider outlines of edit mode, `background` the level stage's background in edit mode (`#rrggbb`, `""` for the game's own `Config.Background`; Play shows the game's own, Stop the host's again; a prefab stage ignores it), and in a prefab stage its look: `stage` is `{background?, grid?}` (`#rrggbb`, grid step in world units). Only the parts present change; the extension takes them from `.weakpixel.json` (`editor.snap`, `editor.prefab`), and a host may follow its light or dark appearance with `background`. In a web page the editor build's screen is transparent (`editor/host`), so the bars around the letterboxed screen show the page's own background. |
| host → game | `visible` | `visible` | The host shows (`true`) or hides the view: hidden, the game ticks at the hidden rate (0: not at all, until the next message) and draws nothing; shown again counts as activity. A host that never sends it is always visible. Without `visible` the message answers `error`. |
| host → game | `create` | `class` or `prefab` | Make a new object of `group:class`, or an instance of the prefab key, at the view center; answered with `create`. |
| host → game | `assetField` | `id`, `field`, `path` | A file was dropped on an inspector asset field (`field`: component, then properties); answered with `field` or `error`. |
| game → host | `field` | `id`, `field`, `value` | Write `value` (an asset key) at `field` of object `id`. |

**Drops.** The file's suffix gives its asset kind (`AssetKinds`). Candidates are object types with a required component that has an asset field of that kind. Exactly one candidate creates an object; several ask the host to choose; none is an error. The new object has every required component at its initial value (the schema's `default`s from `+game:default`, else zero), a `gfx:Transform` at the drop point, and the file's key in the asset field (the component's `ID` if it is of that kind, else the first by name; an `*.anim.json` gives its default clip). A `*.prefab.json` (asset kind `prefab`) is not a field value: it becomes `{"id": "<prefab name>-<n>", "prefab", "components": {"gfx:Transform": <position override>}}`. Go code names the key `editor.TransformKey`. **Default layer.** When the level has a Tiled backdrop whose map has an object layer, a new object lands between the map's tile layers as it would in Tiled: every drawn component it has (`gfx:Sprite`, `gfx:NineSlice`, `gfx:Label`, `gfx:Particles`) gets `Layer` set to the render layer of the nearest tile or image layer below the map's topmost object layer (so `BaseLayer` and the game's `LayerFor` are respected), or the map's lowest render layer when none is below. With several maps (a world) the map containing the drop point is used, else the first. A prefab instance gets it too, as an override written only when it differs from the prefab's own `Layer`. Without a backdrop map or an object layer nothing changes (`Session.DefaultLayer` reports which).

## The extension

The extension is the separate repository [weakpixel/weakpixel-engine-vscode](https://github.com/weakpixel/weakpixel-engine-vscode) (TypeScript, no bundler). The protocol above is versioned together: `bridge.Version` here and `PROTOCOL_VERSION` in its `src/controller.ts`; a mismatch makes the extension refuse the game. `docEdits.ts` and `controller.ts` hold the logic and import nothing from `vscode`, so `node --test` covers them; `levelEditor.ts` (the `CustomTextEditorProvider`), `build.ts` (the wasm build as a VSCode task) and `outline.ts` (the TreeView) are thin VSCode glue. Document edits are computed with `jsonc-parser` `modify` at a JSON path, so a drag or an inspector change is a one-line diff that keeps the file's formatting.

The webview page (`media/`) relays protocol messages between the extension (`{to: "game"}` / `{from: "game"}` over `postMessage`) and the game. It exposes `globalThis.weakpixelHost` for transport and page configuration. The page has its own messages: `{from: "page"}` `started`, `drop` (an Explorer URI and device pixels), `setField`, `revertField`, `openPrefab` and `dropField` from the inspector; `{to: "page"}` `inspect`.

**The inspector reads the document, not the game.** The extension sends the selected object's JSON from the document with its schema (from `ready`), the level's ids and the field errors parsed from the last `applied` (`objects[i] (<id>): <Component>: $.<path>: <message>`). A committed field becomes one `setField` edit; the changed document comes back to the game like any other. So the inspector shows exactly what will be saved, needs no wasm exports, and works while the game is still loading. Widgets come from the `TypeSchema`: numbers (integer checks, minimum, maximum), checkboxes, text, asset keys (with drop), entity ids (a select), `x-enum` integers (a dropdown of the constant names), vector-like objects as one row, short fixed arrays as one row, and JSON text for maps and long arrays. `x-editor` hints (`+game:editor`) refine them: a slider from `min`/`max`/`step`, a color picker, degrees for radians (`unit=deg`), a label, an order, hidden fields and fields shown only while a sibling has a value (`showIf`). They need no protocol change: the schemas in `ready` carry them. Keys typed in it stop at the inspector so neither the game nor VSCode keybindings (Delete) see them.

**Level names.** A level may carry a top-level `name` like a prefab (`Level.Name()`, `Session.Name()`). The extension is meant to list levels by it, with the path as fallback, via a `prefabLabel`-style helper; that change is planned in the extension repository and needs no protocol change.

**Attached objects in the viewport.** A part's `Transform`, and that of any object with `hierarchy:Parent`, is derived by the hierarchy stage, so the handles edit its `Local` instead. A gesture sets the live `Transform` as for any object (so the art follows the cursor), then `syncLocal` converts the field it changes (`Pos` for a move, `Rot` for a rotate, `Scale` for a scale) with `hierarchy.LocalOf(parent's Transform, world)`; the other `Local` fields and `Entity` are untouched. The finished gesture is one `Edit` with component `hierarchy:Parent` and the whole component (the entity as an id), instead of `gfx:Transform`; for a prefab instance or one of its parts it is the override against the prefab (`Part` set for a part), so the file gets `children.<part>["hierarchy:Parent"]` with only the changed fields. A click selects the part under the cursor; Alt+click selects its instance root. When a selected object has a selected ancestor, a move skips it (it follows the ancestor). A selected attached object gets a dotted line to its parent. `bridge.Version` stays 0. A multi-object `*.prefab.json` opens in the prefab stage like any prefab: its document has several objects, the hierarchy stage runs, and the same handles edit the `Local` in the prefab document. Esc does not cancel a drag. Re-parenting in the editor is not built.

**Prefabs in the extension.** A prefab is listed by its top-level `name` (file name as fallback); the game's document parser accepts the key and ignores it, so `bridge.Version` did not change. `src/prefabs.ts` repeats the engine's merge (its cases are the shared fixture `god/testdata/merge-patch.json`, copied to the extension's `test/fixtures/`) and resolves variant chains by reading prefab files from the asset root. The inspector gets an instance merged, with its own overrides: overridden fields are marked and have a revert button, a committed field is written as an override at its path (a field inside an array writes the whole array, which overrides replace), and removing a component the prefab has writes `null`. The custom editor also opens `*.prefab.json`: a prefab is a GOD document, so the game opens it like a level. The commands Create Prefab from Selection, Unpack Prefab and Open Prefab are document edits plus a file write; the game is not involved.

**The editor test game.** `tools/wpix-editor/testdata/game` is a small game for the extension's browser test: built with `-tags editor` it is the editor build, and run without the tag (`go run ./tools/wpix-editor/testdata/game -o <dir>`) it writes its asset library to a folder for the page to serve. Its assets are the generated test library of `testdata/assets` plus `world-1/level-1.level.json` (two plain objects and two instances of `global/prefabs/villager.prefab.json`), and it uses only the engine's own components, so it needs no `go generate`. `go test ./tools/wpix-editor/` opens its level natively and cross-builds it to WebAssembly.

**Assets come from the workspace.** The extension serves the asset root to the webview (`asWebviewUri`), the game reads it with `httpfs` (asset module), and a saved file is sent as `assetsChanged`. Ebiten sizes its canvas from `body.clientWidth`, so the inspector column narrows `body` instead of padding it.

## Tools

`wpix-editor` (`tools/wpix-editor`) is a second binary that opens one file in the tool of its kind on a shared shell, `editor/toolshell`: `wpix-editor <file>`, with no tool names and no modes. It is built from the user's module, like the level editor's game, and runs natively in a window or, built for js/wasm, in the extension's webview.

- **One kind table.** `editor/filekind` (standard library only) lists every file kind once: its suffixes (the engine's own formats `.sheet.json`, `.anim.json`, `.fx.json` and the Aseprite exports in lower case only, the rest in any case), whether it is edited and whether it has sound. The file name is the only rule; the content is never looked at, as for the engine's loaders. `editorapp.Kinds` adds the tool of each kind, its help line and its starter. An edited kind (sheet, anim, fx) has its own editor; every other kind opens in the preview router of `viewer`, so a `*.sheet.json` has one tool, not an editor and an atlas preview. The suffix list lives in its own package because `viewer` routes by it and `editorapp` imports `viewer`. `editorapp.Table` prints the table in the form the extension's file lists are compared with.
- **The tool contract is tested, not only documented.** The shell finds a tool's optional interfaces (`Syncer`, `Initializer`, `Closer`, `Checker`, `DocumentTool`) with type assertions, so a method with a wrong signature would silently drop the behavior; every tool asserts the interfaces it implements at compile time (`var _ toolshell.Syncer = (*Tool)(nil)`), and the viewer does the same for its previewers. `TestToolContract` (`tools/wpix-editor/internal/editorapp`) opens a sample file of every kind of `editorapp.Kinds` in its tool the way the page build does (host transport, host document for an edited kind) and sends every editable panel field back with its own value, a button with `null`; any `error` fails, so a field without its case in `Set`, or one `Set` always refuses, fails in tests instead of on the first click. `TestToolCapabilities` checks that an edited kind's tool is a `DocumentTool` and that only the `view` tool can switch files (a `Closer` without a document), which the extension relies on when it sends `open`. A new kind needs a sample in `contract_test.go`, or the test fails.
- **Missing files start from a starter.** A file of an edited kind that does not exist opens as an unsaved document from its kind's starter (`--image` for a sheet, `--sheet` for a definition, the default effect for an effect); without the flag a missing sheet or definition is an error naming the flag. A starter can name files the first save writes with the document (`FileDocument.AddPending`, served by the overlay until then): a new effect copies its built-in sprite next to it, as Save as does, so a saved effect never names a built-in file.
- **The shell is a `game.Tool` on an engine with no game systems**, like the prefab stage. Assets load through the engine's asset server and real loaders, the content is drawn by the engine's renderer (the texture and atlas previewers spawn one sprite entity; the font previewer draws its samples itself in `Draw`, because a `gfx.Label` lives in screen space and could not pan or zoom), the shell's camera is `Engine.Camera`, and the grid and a tool's overlays are drawn in `DrawFinal` in window pixels. The tick mode is always `TickPause`, so only the engine's own stages run. The engine is configured with `IntegerScale` and a logical size larger than any window, which makes the logical screen the window itself: viewport, mouse and overlays share one pixel space.
- **A tool that installs engine packages does it in `Init`.** `toolshell.Initializer` (optional) is called from the shell's `game.Tool.Init`, before the schedule is built, because `AddRunner` panics after the first update. Its systems still do not run under `TickPause`; the tool steps them itself (the voice previewer calls `Speech.Step` in `Sync`).
- **Tools describe their panel; they do not draw it.** A `Panel` is data (sections of fields: number, checkbox, dropdown, text, button, label) with ids, and `Tool.Set(id, value)` takes a change from either renderer. Natively `debugpanel` draws it with debugui. In VSCode the shell sends the same JSON and the extension draws HTML inputs, so the native build looks like a debug tool and the VSCode one like VSCode. The shell compares the marshalled panel every tick and sends it when it changed; a change of labels only (a mouse readout) at most every 100 ms, the answer to a `set` at once (even unchanged, so an input shows the value the tool accepted). Per-field diffs were rejected: panels are small and the extension rebuilds a section by field id and keeps focus. The widgets are number, checkbox, dropdown, text, button, label, range (`[lo, hi]` that never cross), color (`"#rrggbbaa"`; natively a swatch whose Edit button opens a picker with a saturation and brightness square, hue and alpha bars and a hex field, since debugui has none, and in VSCode the native color input with an alpha slider) and asset (a key from `options`, `kind` image or shader, `thumbs` for entries the page cannot fetch); a tool adds a widget in both renderers in the same change.
- **Two panels over a full-window viewport.** Each `Section` has a `Side` (`left` or `right`, empty is right; `Panel.Check` rejects others): a tool tags its sections and never lays out widgets. The left side holds the view settings (`Shell.ViewSection` is left) and the lists content is picked from, the right side the properties of the selection. The panels are overlays: the camera draws the whole window, and `Renderer.Insets()` (the left and right widths in window pixels, 0 for a panel not shown) only define `Shell.FreeRect()`, the area between them. Fit and auto-fit center the content in that area and zoom from its size (auto-fit refits when it changes); zoom at the cursor, hit tests, gizmos and the grid keep window coordinates, and content may sit under a panel. `debugpanel` builds both debugui windows in one update (so its captured flag covers both) with fixed widths, since debugui windows restart on resize: left `min(w/5, 220)`, right `min(w/4, 280)` UI pixels times the UI scale. The left panel is hidden when the window is under 800 UI pixels (its sections join the right one) or the tool has no left section; the status line is at the bottom of the right panel, or of the left one when there is no right section. The `wpix-editor` tools turn on the screenshot hotkey ([`game.DevScreenshotKey`](../guide/engine/engine.md#hotkey-and-environment-variables): F12, F9 in a browser) next to the Screenshot button of the view section. Tab (a shell shortcut, which tools must not bind) hides both: the renderer is neither updated nor drawn and the insets count as 0. `Toolbar` is one row of icon buttons centered at the top of the free area, so it follows the insets and Tab. A dropdown with `Field.List` rows (`Field.AsList`) is a list: `debugpanel` draws a label, then a scrollable panel of that many rows (fewer when there are fewer options) with one button per option, the selected one marked `> `, and a click sets the option index like the dropdown does. Lists put a `(none)` option first when the selection can be cleared. `Check` rejects `List` on any other widget. The JSON gains only `side` and `list`, which the extension ignores (one column, a list stays a dropdown), so the protocol and `bridge.Version` are unchanged.
- **Three document backends.** A `MemoryDocument` is an untitled document with the undo stack of `FileDocument` (shared code), no file and no host; it is dirty from the start and `Shell.Create` turns it into a `FileDocument`.
- **Two document backends.** A `DocumentTool` edits a text file through `Shell.Edit(text)` with the bytes of its format's encoder; the shell never diffs. `FileDocument` (native) keeps its own undo stack, saves with Ctrl/Cmd+S, marks the title dirty, reloads a file changed on disk when it has no unsaved edits and reports the conflict in the status line when it has. `HostDocument` (VSCode) sends `edit` and gets `document` back, ignoring the echo of its last edit, as `Session` does; VSCode owns undo and save.
- **One document model.** `toolshell.Model[F]` is the model of a tool whose state is one decoded file: `File`, an `Encode` func and `Emit` (the tool passes `Shell.Edit`). `Model.Do(edit)` runs a change on `File`, encodes it and emits the text, so one change is one document edit. Its `toolshell.DocStatus` (`Loaded`, `Stale`, `ReadOnly`) refuses edits with `ErrReadOnly`, `ErrStale` or `ErrNoDocument` through `Editable`. Decoding stays with the tool, because it also loads what the file names. The sheet and anim tools embed `Model`; the fx tool embeds only `DocStatus`, since its model is the emitter list and a copy of the selected emitter.
- **Shared texture drawing.** `editor/viewkit` holds what the tools that show a texture share: `Texture` (one sprite entity with its top-left corner at world (0, 0), pinned at the center of its visible part, since the engine culls a sprite by its position alone), `Frames` (frame outlines, label modes, hover, click selection and the left Frames list) and `Labels` (overlay text). The texture, atlas and shader previewers and the sheet tool use `Texture`; the atlas previewer and the sheet tool use `Frames` (ids `atlas.labels`, `atlas.frame` and `sheet.labels`, `sheet.frame`); every previewer that writes overlay text uses `Labels`.
- **`view` is the preview of every kind that is not edited**, with a previewer per kind (`viewer`: texture, atlas, font, Tiled map, tileset, world and shader; an Aseprite export goes to `animedit`, a voice or a dialogue to `voiceview`), chosen from `filekind` when a file opens. An edited kind is refused: it opens in its editor. An editor never routes; it runs on its own shell with its document. The atlas previewer lists frames from `render.Atlas.Order` (file order), the font previewer reads the face from the engine's font store. Overlay text in window pixels is rendered once to small images (Go Regular, so no font file is needed), since `text.Draw` cannot target a `FinalScreen`. An Aseprite export plays in the anim tool read-only (`animedit.NewPreview`, which loads the clip set in the viewer's scope) by treating the export as an empty definition of itself: edits fail with `ErrReadOnly`, so there is one code path for playback. The host's `open` message switches the viewer to another file in place: the previewer's entities are deleted, the viewer's asset scope is released (the old file's assets unload unless the new file holds them too) and the new file is framed, while the grid and background stay. The shader previewer (`.kage`) builds on the texture previewer: the sprite gets the shader and a `Params` value per `+shader:param` marker (a number or slider, toggle, angle in degrees or color widget; four plain numbers without markers), "Enabled" compares with the plain texture, and the texture is the built-in sample (served from the overlay) or any project image. A compile error or a marker problem is shown in the panel and sent as an `error` naming the file (and the marker line). `Time` is the engine's simulation time, which keeps running under the shell's pause; the values are not saved. A later previewer (M7 bindings) is one more entry in the viewer.
- **The Tiled previewers load with the engine's loaders and draw objects as overlays.** A map (`*.tmj`) and a world (`*.world`) are loaded with `LoadMapSync` and `LoadWorldSync` in the viewer's scope and spawned with `tilemap.Spawn` and `SpawnWorld`, so tile and image layers are the same `TileLayer` entities the game draws (tints, opacity, shaders and parallax as in the game). Objects are not entities in the engine, so they are window-space outlines (`viewer/shapes.go`: rect, ellipse as 24 segments, polygon, polyline, a cross for a point, the box of a tile object or text; hit test by box, point-in-polygon, or 5 device-independent pixels for lines and points, where a point's cross has 4 px arms), named with the same label cache and size rules as atlas frames. Overlay labels are 13 px Go Regular on a dark plate, in device-independent pixels: the final screen is in device pixels, so the label cache renders at 13 times the display scale factor (re-rendering when it changes), and the 24 px minimum width a frame or object needs for an unforced label scales the same way. Each layer's checkbox is Tiled's own `visible` (read from the file again, since the loaded map has it composed with the groups); a group's checkbox hides its children, and the toggles are kept by layer path across a hot reload. A tileset (`*.tsj`) is one sprite entity per tile on the tileset's grid (`columns`, else a square-ish grid for a collection), so single-image tilesets and collections look alike; animated tiles take `Tile.FrameAt` of a clock the previewer advances by 1/60 s per tick (the "Animate" checkbox pauses them at frame 0). A world shows each map's rectangle with its file and levels. A click selects and a double click opens the first level of a map, so hovering and selecting are safe. A hot reload (the asset version of the map, tileset or world changed) deletes and spawns the entities again and keeps the camera. Tiled files are never written (Tiled is the editor).
- **Voices and dialogues preview with sound** (`editor/voiceview`, routed by `viewer`). A page or window starts with sound when its first file's kind has sound (`filekind.Info.Sound` turns off `game.Config.NoAudio`, natively and in the js/wasm build), because `NoAudio` is fixed when the engine starts and package speech must be installed before the schedule is built. The viewer's `Init` then creates the voice previewer, whose `Init` calls `speech.Install`, and keeps it across files; a viewer that started without sound refuses a voice or a dialogue, so the host reloads the page for it. since the shell pauses the game, `Sync` calls `Speech.Step` with one tick. A `*.voice.json` speaks the panel's line (text field, speed, Say, Skip, Stop) on an entity with a `speech:Speaker` and a `gfx.Label` but no `Transform`, so the renderer does not draw the label; the tool draws the shown text itself in `Draw`, wrapped once over the whole line so lines do not move while it types (Go Regular at 16 device-independent pixels), and under it a piano roll of the line from `Speech.LineNotes` (time left to right, pitch bottom to top over at least an octave, a color per instrument) with a playhead from `Speech.LinePosition`. A `*.dialogue.json` plays in a `speech:DialogueBox` entity with a name label (Next, Restart, Stop; Next after the end plays again), its status line names the line (from `LineStarted`) and the speaker. A reloaded voice says the line again; a reloaded dialogue restarts. In a webview the sound starts after the first click inside the canvas (a click on the panel does not unlock the page's audio, the voice library's finding); the panel says so. Nothing is written: voices and dialogues are edited in the library's Voice Editor. It is a `Closer`, so the viewer can switch files.
- **Which levels use a map.** Only in a library package: the `<map base>.level.json` beside the map (the engine spawns it with the map, see `LoadMap`), and the package's `<pkg>/<pkg>.level.json` when its backdrop (`<pkg>/<pkg>.tmj`, else `.world`) is or lists the map. The previewer looks the files up with `Shell.Files()` (the page build) or `fs.Stat` (native); it lists no directory.
- **Overlay primitives.** `Shell.FillRect` draws axis-aligned rectangles; `Shell.StrokeLine` and `Shell.StrokePolyline` draw lines of any angle and width in window pixels (the shared 1×1 white pixel, scaled and rotated, with square ends and no anti-aliasing). `Shell.WindowRect` and `Shell.WindowPoint` map world positions to window pixels.
- **debugui stays out of the wasm build.** debugui is imported only by `toolshell/debugpanel` and `tools/wpix-editor/internal/native`, and Cobra, which the command line uses, only by `tools/wpix-editor/cmd`. A game module that builds `wpix-editor` for js/wasm (the extension does) then needs no new `go.sum` entries (neither for debugui nor for Cobra), because Go only asks for modules of packages it loads. The native build needs debugui in the game module's `go.sum`: the module runs it as a Go tool (`tool` directive, `go get -tool`), which adds debugui to `go.mod` and `go.sum`. `internal/deps` enforces both.

**Tool protocol (js/wasm only).** The same page transport as the level editor (`weakpixelHost.fromGame` and `toGame`), JSON objects with a `type`. The page connection, the host's settings and the protocol version are in the leaf package `editor/hostlink` (`hostlink.ConnectPage`, `hostlink.Version`), which the bridge uses too, so a tool links neither the bridge nor the level editor. The page fields are `path` (the file's asset key), `untitled` (bool), `assetBase` and `files`; there is no tool field: the wasm build picks the tool from the file name in `path` through the kind table (`hostlink.Path`). With `untitled` true the file has no name on disk yet and opens as an untitled document from its kind's untitled text; only a particle effect can be untitled (VSCode's "New Particle Effect" sends `path` `untitled.fx.json`), and its `ready` has `path` `""`. These are page fields, not messages, so `hostlink.Version` stays 0. A level editor page and a tool page never share a game, so message types may repeat. `bridge.Version` is sent in `ready`.

| Direction | Type | Fields | Meaning |
| --- | --- | --- | --- |
| tool → host | `ready` | `version`, `tool`, `path`, `document` (bool), `panel` | First tick, and after every `open`. `tool` is the kind's tool: `sheet`, `anim`, `fx`, or `view` for every previewed kind (the host allows `open` for `view`). `path` is the file's asset key, `""` for an untitled document. `document` says the tool wants the file's text. |
| tool → host | `panel` | `panel` | The panel changed. |
| tool → host | `edit` | `text` | Replace the document with this text (document tools). |
| tool → host | `create` | `path`, `text`, `files` (`[{path, data}]`, data base64) | Write a new document and the files it names, asking the user before overwriting, then open it in the tool and close the untitled one (an untitled tool's `ready` has `path` `""` and `document` false). Paths are asset keys. |
| tool → host | `open` | `path` | Ask the host to open the file at asset key `path` (a level found by a Tiled previewer, a map to preview). A request: the host decides how the file opens (a `.level.json` in the level editor, a previewable file in the Preview panel, anything else as text) and an unknown key is the host's error. Natively there is no host: `Shell.OpenFile` puts "Open <key> in your editor" in the status line. The host's `open` below has the same name and the opposite direction. |
| tool → host | `screenshot` | `id`, `png` (base64), `width`, `height`, `tick`, `error?` | The answer to a host `screenshot`, or (`id` `""`) a capture the tool took itself, from the Screenshot button or the hotkey: the same message as the level editor's. The tool's content only, at window size; the grid, the overlays and the panels are never in it. Under a host the shell installs the screenshot sink, so no file is written. |
| tool → host | `error` | `message` | A message failed, or the file or an asset failed to load. |
| host → tool | `document` | `text` | The document's current text (after `ready`, and after every change). |
| host → tool | `set` | `id`, `value` | A widget changed; answered by `panel` (or `error`). A button's value is `null`. |
| host → tool | `assetsChanged` | `paths` | As for the level editor. |
| host → tool | `screenshot` | `id`, `target?`, `scale?`, `keepAlpha?` | As for the level editor; answered by `screenshot`. |
| host → tool | `open` | `path` | Show the file at asset key `path` in the same game, without a page reload; answered by `ready` for it (after an `error` if it fails to load). Only `view` can switch files (a `toolshell.Closer`); other tools answer with an `error` and keep their file. |

The view section every tool shows (grid, cell and offset, background, zoom, Fit, 1:1 and Screenshot) comes from `Shell.ViewSection`, and the shell handles its `set`s. A checker background is a world layer, since the grid and overlays are drawn after the world: the `fx` tool adds a generated checker sprite on the lowest layer (the `anim` tool does not: the Dark, Black, Gray and Light backgrounds are enough for pixel art). A tool that reads a file as raw bytes (not through a loader) uses `Shell.FS`, the asset filesystem the command passes in `Config.FS`.

### The fx tool

`wpix-editor <file>.fx.json` (`editor/fxedit`) makes a particle effect: a `*.fx.json` file holding one to eight `fxfile.Emitter` values ([format](../guide/engine/particles.md#the-effect-file)). Everything but `tool.go` is plain Go without Ebiten.

- **The model is the whole file.** The file is small and fully owned by the tool, so there is no text splice: `fxfile.Decode` reads it and `fxfile.Encode` writes the canonical form, which the tool also uses as the document text. An edit replaces the document with the encoded emitter, so undo, dirty state and the diff in VSCode work on the file as any other. The tool's `Emitter` is `fxfile.Emitter` itself: authored units (degrees are the file's, radians the simulation's) and sprite and shader as asset keys.
- **Several emitters.** `State` holds the emitter list (`Ems`), the selected index (`Sel`) and a copy of the selected emitter (`Em`), which every panel field edits. The Emitters section (a list on the left) selects, adds, duplicates, deletes and reorders (one document edit each); the Emitter section on the right edits the name and the draw layer (one document edit each). Mute and solo are preview-only: `Muted` never reaches the document, and the preview text leaves out muted emitters (all muted plays one that spawns nothing). The Live readout and the Max cap are sums over the emitters; Save as exports every built-in sprite (`ExportAll`: `name.png`, then `name-2.png`, ...).
- **The preview is the real asset.** The tool writes the encoded text into `toolshell.OverlayFS` as `fx-builtin/preview.fx.json`; the first publish loads it with `particles.LoadEffect`, later ones call `Changed` so the engine's hot reload applies them. A drag does not restart the effect; only a cycle key does (see the renderer notes).
- **Presets and built-in sprites are code.** The presets are Go values tested to be valid and to play, each emitter on its own: single emitters (smoke, sparks, fire, rain, snow, ...) and whole effects of up to eight named emitters (campfire, fireworks, thunderstorm, confetti, magic portal, dragon breath, and supernova, which uses all eight). Burning scraps shows the built-in Burn shader, which reads the tint's alpha as the part not burned yet (a particle shader's only per-particle input is its tint). Applying a preset replaces the whole effect in one edit and clears the mutes and the selection; a single-emitter preset applies Keep to the selected emitter, a multi-emitter one ignores it. Reset (Emitters section) is one edit back to the default preset's emitter. The sprites (soft circle, dot, spark, ring, star, square, streak, flake, heart, plus) are drawn with `image/png`; the built-in shaders are embedded Kage files (`fxedit/shaders/`, so far `burn.kage`). While editing they are served from `toolshell.OverlayFS` under `fx-builtin/`, which the engine loads like any asset. Save as copies the ones in use next to the effect (`name.png`, `name.kage`, then `-2`, ...) and rewrites the keys, so a saved effect never names `fx-builtin/`; a saved file that does gets a Problems finding.
- **One panel edit is one document edit.** The preview controls use `particles.Clock`, a world resource the engine registers at its defaults: scale, pause, step and a seek that restarts and replays up to 600 ticks. The preview entity is one entity without a `Seed`, so its pool seed is stable and a scrub is deterministic.
- **Shader parameters** come from `shaderparam.Parse` (`internal/shaderparam`, [shaders.md](../guide/engine/shaders.md#parameter-markers)); the tool reads the shader's source when it changes or its file does, and without markers shows four plain numbers.
- **Untitled effects.** In VSCode, New Particle Effect starts the tool on a `MemoryDocument` holding the smoke preset (natively a missing file starts from the same effect, see the starters above). Save as writes the effect and sprite natively through `Shell.Create` and continues on a `FileDocument` with the undo history; in VSCode the wasm build cannot write, so `Create` sends the `create` message and the extension writes and reopens. The target is asked about before it is overwritten (the button becomes Overwrite?). `bridge.Version` is unchanged.
- **A document that does not parse** is handled as in the anim tool; a missing image or shader is a Problems finding and a placeholder, not a failure.
- **Not built:** curves and gradients over life, sub-emitters, trails and flipbooks (not in the engine), A/B snapshots, atlas frames in the image picker (only files), a live level as background.

### The anim tool

`wpix-editor <file>.anim.json` (`editor/animedit`) edits an [animation definition](../guide/engine/animation.md#animation-definition-animjson) on its Aseprite sheet.

- **The model is the file.** The tool holds the decoded `animfile.File`. Every change is a function on it, then `animfile.Encode`, then one `Shell.Edit`; an undo, a change on disk or the host's `document` comes back through `Load`. The file it writes is one the loader and `wpix anim validate` accept, and `animfile.Diagnose` is the single source of the findings both print (the editor shows them in a Problems section).
- **The sheet is read for tags and pixels; the definition is not loaded through the asset server.** The sheet's JSON goes through `animfile.DecodeSheet` (tags, trim offsets) and the sheet is loaded as a clip set for the frame sprites, so the PNG and the sheet hot-reload. The loader would reject an invalid definition, and a half-edited file must still draw.
- **World space is pivot space.** The shown clip's pivot is world (0, 0) and `body` and shape rects are used as world rectangles unchanged, so a drag in whole world pixels is the new `rect`. Flip H mirrors the drawing around x = 0 and never changes the file. `anim.PivotOrigin` turns a pivot into `Sprite.Origin`; the loader uses the same function.
- **One edit per gesture.** A drag previews and writes on release, so one drag is one undo step. A box drawn on frame n becomes `frames {from: n}`; "Copy to this frame" keys a box per frame.
- **An invalid document is shown, not overwritten.** If the text does not parse the tool keeps the last good version dimmed, says why in the status line and ignores edits until a valid text arrives.
- **Playback runs on the tool's clock.** The shell ticks paused with no animation system, and the editor needs stepping and scrubbing, so the tool keeps its own time and asks `anim.Clip.FrameAt` (built from the resolved durations and loop mode) for the frame.
- **New definitions.** `--sheet <export.json>` with a missing file starts from `animfile.Starter` as an unsaved document; Ctrl/Cmd+S creates the file.

### The sheet tool

`wpix-editor [--image <texture>] <file>.sheet.json` (`editor/sheetedit`) edits a [grid sheet](../guide/engine/asset-kinds.md#grid-sheet). Everything but `tool.go` is plain Go without Ebiten.

- **One reader and writer.** `sheetfile` (stdlib only) holds the format: `Decode` and `Validate` (the loader's checks, all problems at once), `Encode` (two-space indent, zero margin and spacing left out) and the layout (`File.Layout`, `Grid.Rect`, `Grid.At`). The atlas loader in `render` expands its frames with the same `Layout`, so the tool shows the frames the game gets.
- **The model is the file.** A panel change is a function on `sheetfile.File`, then `Encode`, then one `Shell.Edit`, so undo, dirty state and the diff in VSCode work on the file as for any other document. Values the format refuses (a frame size below 1, a negative margin or spacing, a fraction) are rejected by `Set` and nothing is written. The pivot is kept by the encoder and not edited. A document that does not parse is handled as in the anim tool: the last good sheet stays, edits fail with `ErrStale`.
- **The texture is a sprite at the origin.** It is loaded with `render.LoadSpriteSync` from the sheet's folder and the `image` value, with its top-left corner at world (0, 0), so a world point is an image pixel; `viewkit.Texture` keeps it from being culled. A missing or changed image is a Problems finding and a hot reload, not a failure. The grid is a window-space overlay drawn by `viewkit.Frames`, as the atlas previewer draws its frames: index labels, hover, click selection and the Frames list, with the leftovers dimmed and, below 4 window pixels per cell, only the border of the grid. The list follows the grid after every edit and keeps a selection whose index still exists. Above `sheetedit.MaxListed` (4096) frames the list stays empty and only the cells on screen are outlined, so a frame width of 1 typed on a big image does not send a list of thousands of entries to the panel.
- **New sheets.** `--image` with a file that does not exist starts an unsaved document (`sheetedit.NewSheet`, `sheetfile.Starter`). In VSCode the extension writes the starter text itself, so the protocol and `bridge.Version` are unchanged.
- **Not built:** pivot editing, frame names, trimming empty cells.

## Not built yet

- A start zoom for the prefab stage, and a prefab shown in the context of a level.
- Listing the workspace's files over HTTP, so that files created in VSCode are in the asset library without a rebuild.
- Snapping in the inspector, label and anim-box picking, per-axis scale handles, rotating or scaling several objects at once.
- Editing several selected objects at once in the inspector.
- Running the extension's own tests inside VSCode (`@vscode/test-electron`): only the VSCode-free parts and the webview page are tested automatically.
